# Remote Screen System (RSS) – Internship and Exam Project

Remote Screen System (RSS) is a web-based application developed during an internship as part of an IT education programme and later extended for use in a final exam project.

The system was deployed on company domain infrastructure for demonstration and evaluation purposes.  
Although not used as an active production system, it reflects a realistic full-stack implementation outside a local development environment.

---

# Project Context

This project was:

- developed during an internship placement
- extended and submitted as part of a final exam project
- deployed on a company-hosted domain
- implemented independently by a single developer

The goal was to design and implement a structured remote screen management solution following real-world architectural practices.

---

# Purpose of the System

The Remote Screen System provides a centralized interface for managing and displaying remote screen content in a controlled environment.

Typical use cases include:

- remote screen monitoring
- centralized display control
- structured screen configuration
- controlled presentation of remote content
- demonstration and evaluation of screen-management workflows

The system was designed as a maintainable and extensible solution rather than a prototype-only academic exercise.

---

# Features

Core functionality includes:

- remote screen configuration interface
- centralized screen control logic
- structured backend communication
- modular service-layer architecture
- separation between UI and application logic
- API-driven data flow
- deployable web-based interface

# Architecture Overview

The solution follows a layered architecture separating responsibilities between:

Frontend  
Backend services  
Data models  
API communication  
State handling logic  

Typical responsibilities include:

Frontend:

- rendering remote screen information
- handling navigation and interaction
- presenting screen configuration controls

Backend:

- managing screen state
- processing screen-related requests
- exposing structured endpoints

Shared layers:

- DTO models
- request/response contracts
- service abstractions

# Example Workflow

Typical system behaviour:

1. user configures screen behaviour
2. frontend sends structured requests to backend
3. backend processes configuration logic
4. system updates remote screen state
5. interface reflects current configuration
